## 재개 검증 경로

`tools/reconcile_runtime.py`는 기본 모의 대사다. 실제 반영은 사용자 위임을 확인한 호스트가 두 적용 플래그를 사용한다. 적용 전에 봇·shadow 정지, 원격 소유 해제, 거래소 wait/watch 주문 없음, 잔고·현금·평균 원가 불변을 확인하고, 같은 주문 ID의 수수료·실제 상세 체결까지 다시 조회한다. 포화된 주문 조회 구간은 시간을 분할하며 완전성을 증명할 수 없으면 차단한다.

`v5/reconcile.py`는 확인된 체결만 시간순 재생하고 중복을 막는다. `v5/reconciliation_guard.py`는 원본 해시·원본 시각·현재 원격 체크포인트·증명 ID를 각각 고정하고, 저장된 체결을 독립 재생해 목표 수량·원가·손익·재진입·재생 포인터를 확인한다. 확인 사실을 적은 JSON을 믿고 통과시키는 방식이 아니다. 원본 집 장부와 회사 마지막 장부가 다르다는 사실을 숨기지 않는다.

적용 중 `data/reconciliation/APPLYING`을 두고 백업 후 원자 교체한다. 실패 시 원복하고, 원복이 확인되지 않으면 표식을 남긴다. SessionGuard는 대사 중·인계 중·미완료 복원 표식이 있으면 시작과 주문을 막는다. 정상 검증 후에만 기존 단일 실행권 CAS 경로로 재개한다.

## 다음 PC 이동에서 생성·전달할 자료

`tools/handoff_cli.py publish --publish --stop-source`는 미확정 주문이 없을 때 정상 종료 요청 → 종료 확인 → 최종 ZIP 생성 → 설정·장부·보호·PnL 기초 안정성 검사 → 수신자 공개키 암호화 → 지정 Git 원격의 전용 브랜치 전송을 이어 수행한다. 강제 종료·주문 취소·원격 실행권 강제 덮어쓰기·자동 재시작은 하지 않는다.

Git에 올리는 자료는 **암호문과 공개 영수증**이다. 장부·주문·실행 설정·손익 기초파일의 원문과 개인키는 올리지 않는다. 수신 PC의 공개 인증서를 최초 등록한 뒤 해당 개인키로만 복호화한다. 집 수신자는 등록했고 공개 프로필은 `handoff/recipients/home.json`이다. 회사 수신 PC는 그 PC에서 개인키를 한 번 생성하고 공개 인증서만 등록해야 한다.

담당 AI는 송신 결과의 **브랜치·암호문 해시·수신자 지문**을 공통 인계 문서에 적고 Git에 보관한다. 다음 PC에서는 공통 문서를 읽고 해당 브랜치를 받아 기본 dry-run 검증 후 `receive --apply`로 상태만 복원한다. 실행 코드는 최신 Git에서 받는다. 보호 목록은 양쪽 config와 파일의 합집합으로 유지한다. 실제 계좌·원격 체크포인트·손익 기초를 다시 확인한 뒤 봇을 시작한다.

원문 ZIP과 정규화 JSON 체크포인트의 해시는 서로 구분한다. 참고용 ZIP은 최종 복원으로 통과하지 않는다. `.env`·인증 저장소·session_git·중첩 인계 ZIP은 제외하며 복원 도중 실패하면 pending 표식을 남겨 혼합 상태로 거래를 시작하지 못하게 한다. 전송 자체의 성공을 수신·복원·거래 시작의 성공이라고 쓰지 않는다.
