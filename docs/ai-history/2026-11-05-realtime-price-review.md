# 2026-11-05 화면 가격 지연·손절 체결가·실시간 연동 검토

사용자 질문: 화면 새로고침 가격과 실제 가격의 시차, 실시간 연동에 필요한 장치, 손절·익절 주문가격과 실시간 가격 차이. 코드와 업비트 공식 문서를 읽은 검토이며 이번에 매매·화면 코드나 설정을 변경하지 않았다. Claude 새 응답·합의도 없다.

## 1. 확인한 현재 경로
- account_sync.py snapshot은 잔고·시장목록·REST ticker를 차례로 조회하고 account_live.json을 쓴 뒤 정상 시5초 대기한다.5초는 전체 조회시간을 포함한 최대 지연 보장이 아니다.
- bot.holding_rows는 계좌 파일이120초 안이면 그 파일 가격/평가액을 사용하며, 오래되면5분 주기 PnL summary 행으로 되돌아간다. 원가 선택은 별도로 pnl→봇→거래소 평균이며 시세 신선도와 구분한다.
- bot.run 화면 파일은30초 목표 주기로 다시 생성한다. 브라우저 자동 새로고침 기본180초(사용자 localStorage 선택값으로 달라짐). 따라서 최신 계좌 파일과 화면에 보이는 숫자가 다를 수 있다.
- 수동 새로고침은 로컬 POST /refresh 뒤4초 타이머로 location.reload한다. 최신 파일이 완성됐다는 응답을 기다리는 버전 확인 방식이 아니므로, 루프가 막히면 이전 HTML을 다시 볼 수 있다.
- 손절/이익보호 판단은 화면 HTML을 읽지 않는다. live.stop_check는 별도 REST ticker의trade_price와 stop_limit를 비교하며 실행권·보호·미확정 주문·가용 잔고를 확인해 매도한다.
- 실제 설정 stop_check_seconds 기본3, strategy.stop_seconds30 확인. 전자는 손절/이익보호 최신가 확인 목표, 후자는1분봉/추적 등 trail_check 목표다. 둘 다 같은 메인 루프 안이다. 직접주문 보호 스캔, 요청 처리, 종목별 봉 조회, 문서/화면 생성·통신 등이 다음 확인을 늦출 수 있어 “정확히3초마다”나0지연을 보장하지 않는다.
- upbit.market_sell은ord_type=market, 매도 수량만 전송한다. 화면 가격·감지 가격을 매도 지정가로 전송하지 않는다. 일반적으로 마지막 타인 체결가와 매도 호가가 다르고, 주문량·호가잔량·전송 동안의 이동에 따라 실제 가중평균 체결가가 달라진다.
- 화면 지연, 손절 감지 지연, 매수/매도 호가 차이, 체결 미끄러짐은 서로 다른 원인이다. WebSocket으로 앞의 두 원인을 줄여도 체결 가격 차이0을 보장하지 않는다.

## 2. 권장 연동 구조 — 아직 미적용
특수 하드웨어보다 소프트웨어의 지속 연결과 시간 검증이 우선이다.

업비트 Public WebSocket(ticker/trade + orderbook) → 하나의 시세 캐시 → 화면 숫자와 위험 판단의 공통 입력
- 보유·후보 종목을 구독하고 불필요한 연결 중복을 줄인다. 공통 캐시는 종목·마지막 체결가·최우선 bid/ask·호가 잔량·거래소 생성 시각·로컬 수신 시각·연결 상태를 구분해 보존한다.
- 거래소의 trade_timestamp와 메시지 timestamp, 로컬 수신시각은 다른 의미다. 거래가 적은 종목의 마지막 체결이 오래됐다는 이유만으로 연결이 끊겼다고 단정하지 않는다. ping/pong 연결 상태와 가격 자체의 신선도를 각각 평가한다.
- 정적 파일 전체 새로고침 대신 localhost HTTP에서 읽기 전용 SSE 또는 로컬WebSocket으로 변경 숫자만0.5~1초 목표 간격으로 표시한다. 시세 수신은 메시지별 처리하되 UI는 묶어서 갱신할 수 있다. 가격시각·수신 후 경과시간·조회 방식/지연 상태를 표시한다.
- 화면 상단은 마지막 체결가, 즉시 매도 가능 참고가는 최우선 매수호가, 실제 청산 예상은 수량별 호가 깊이를 반영한 별도 값으로 이름을 구분한다. 현재가와 bid를 몰래 서로 대체하지 않는다.
- 위험 판단은 느린 전체 종목 순위 계산·문서 작성·화면 재생성과 분리한다. 화면과 같은 캐시를 보되 주문은 기존 단일 실행권/멱등성/미확정 대사/사용자 보호를 유지한 주문 경로 하나로만 낸다. GUI나 시세 수신 스레드가 직접 별도 주문하는 구조는 피한다.
- 단절·오래된 시세에는 재연결/스냅샷/REST 재조회로 복구하고 화면에 지연 표시. 데이터 불명확 시 신규 매수를 보류하되 시세 연결 장애 때문에 기존 위험 청산까지 무조건 비활성화하지 않는다. REST 대체 조회로 계속 관리한다.
- 실제 청산 트리거를 last trade에서best bid나 예상 체결가로 바꾸는 것은 별도 매매 정책 변경이다. 이번 설명만으로 적용하지 않고 기준을 명시해 검토한다.
- 내 주문은 서버에서 인증한 Private WebSocket myOrder로 수신하거나 기존 REST 주문 조회로 대사한다. 재연결 후 REST로 실제 주문 상태/미체결/부분 체결을 확인한다. 가격은공개데이터지만 개인 주문 인증키/JWT는 브라우저에 넘기지 않는다.

## 3. 필요한 측정과 적용 순서
1. 거래소 메시지 생성·로컬 수신·화면 반영·조건 감지·실제 HTTP 전송·거래소 체결을 각각 기록한다. 로컬 구간 지연은 monotonic 시간으로 측정하고 거래소와 비교할 시스템 시각은 동기화한다. 지연 원인을 하나의 슬리피지 숫자로 합치지 않는다.
2. 우선 시세 전용 연결/읽기 전용 화면을 검증한다. 메시지 역순·중복/연결 단절/무체결 종목/잘못된 종목/오래된 캐시/재접속/조용한 연결을 점검한다.
3. 위험 엔진 시세 입력 교체는 별도 검토 후 적용한다. 기존 가격 기준·손절선은 유지해 데이터 전달 변경과 정책 효과를 섞지 않는다. 부분 체결·조회 실패에서 중복 주문이 나가지 않는지 검증한다.
4. API수신·처리·전송의 실제 지연과호가 잔량을 측정하기 전 특정 밀리초/체결가 보장을 하지 않는다. 현재 PC와 네트워크로 먼저 검증할 수 있으며 상시 가동 서버는 안정성 선택지이지 체결가 일치 장치가 아니다.
- 이번 작업에서 테스트 주문·WebSocket 실접속·배포·프로세스 재시작·실거래 설정 변경은 하지 않았다. 코드 검토와 설계 설명이며 수익성 또는 실시간 성능 검증이 아니다.
